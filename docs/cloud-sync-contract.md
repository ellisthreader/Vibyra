# Cloud sync contract (zero-setup cloud computer)

Goal: the Mac keeps every project (committed + uncommitted work, honouring a secrets denylist) and optionally its
agent conversations ready on the account's cloud computer, so when the lid closes the phone opens the same code in the
cloud with nothing set up. Changes made in the cloud come back to the Mac for review. Parent docs:
`docs/cloud-computer-contract.md`, plan `~/.claude/plans/exacrlt-this-can-you-cozy-clock.md`.

Rules for every worker: new behaviour in NEW small files (200-line standard); re-read a file right before each targeted
edit (peers edit this checkout in parallel); never `git stash`; never run the bare backend suite (one file or
`--filter`, `php -d memory_limit=1G vendor/bin/phpunit --colors=never <file>`); do not touch files owned by another
worker (table below); Cargo env: `export DEVELOPER_DIR=/Library/Developer/CommandLineTools SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk CC=/Library/Developer/CommandLineTools/usr/bin/clang CFLAGS="-isysroot /Library/Developer/CommandLineTools/SDKs/MacOSX.sdk"` and put `/Library/Developer/CommandLineTools/usr/bin` first on PATH, use `/Library/Developer/CommandLineTools/usr/bin/git`, script edits with node not python3; format only the Rust leaf files you edited (never rustfmt a crate root). No deploys (the lead deploys). Report each item as implemented+tested (which tests), implemented+untested (why), or not done. Never claim real Fly/phone behaviour.

## Identities

- `projectKey`: 32 lowercase hex = first 32 hex chars of `sha256("vibyra-project:" + <Mac project id>)`.
- `name`: the cloud folder `/data/projects/<name>`; regex `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`, no `.lock` suffix. The Mac proposes a slug of the
  project name (`[a-z0-9_-]`, max 40); the backend grants the final name (unique per account; on a clash with another `projectKey` it appends `-<first 4 hex of projectKey>`).
- Mac device: `deviceId` = uuid generated once per Mac install (stored beside the sync state). `macId` below = that uuid.
- Seq: per project, per direction (`up` = Mac to cloud, `down` = cloud to Mac), per kind (`code`, `transcripts`); integers starting at 1.

## Crypto (identical on all sides; both sides ship test vectors in `docs/cloud-sync-vectors.json`, written by `sync`, consumed by `vm`)

Key pairs are X25519. The VM generates its pair at first boot (`/data/.vibyra-sync/key`, owned by uid 1001, mode 0400, never leaves the VM); its public key (64 hex) is sent with `POST sync/key`. Each Mac generates its own pair (secret in the OS keychain, or a 0600 file in the app data dir where no keychain exists); the public key is registered with `PUT sync/macs/{deviceId}`.

Sealed stream format (`VSYNC1`), recipient public key `R` (32 bytes):
1. generate ephemeral X25519 pair `(e, E)`; `shared = X25519(e, R)`.
2. `key = HKDF-SHA256(ikm = shared, salt = E || R, info = "vibyra-sync-v1", len = 32)`.
3. Output = `"VSYNC1\n"` (7 bytes) `|| E` (32 bytes) `||` chunks. Plaintext is split into chunks of at most 65536 bytes (an empty plaintext is one empty final chunk). Chunk `i` (0-based) is encrypted with ChaCha20-Poly1305 (RFC 8439), nonce = `00 00 00 00 || u64_be(i)` (12 bytes), AAD = the 39-byte header (`"VSYNC1\n" || E`) `|| final` where `final` is one byte `0x01` for the last chunk and `0x00` otherwise. Each chunk is written as `u32_be(len(ciphertext_including_16_byte_tag)) || ciphertext`.
4. A reader must reject: wrong magic, a chunk length over 65536+16, a missing final chunk, trailing bytes after the final chunk, and any failed tag.
The upload `sha256` parameter is the lowercase hex SHA-256 of the whole sealed stream (ciphertext), so the server can verify integrity without reading plaintext.

## Plaintext artifacts

- `kind=code`: a `git bundle` (v2/v3, whichever git writes) containing exactly one ref `refs/vibyra/snap` (up) or `refs/vibyra/cloud` (down). `head` = the 40-hex commit sha at that ref. A snapshot commit's tree is the FULL project tree (tracked + untracked, ignored files excluded, secrets denylist applied, `.git` excluded, symlinks skipped, files over the per-file cap skipped); its parent is the previous snapshot commit of that chain. `baseSeq = 0` means a full bundle (no prerequisite); otherwise the bundle is incremental against the head of `baseSeq` of the same chain and the receiver must already have it.
- `kind=transcripts`: a tar (ustar, no compression) of regular files only: `claude/<id>.jsonl` and `codex/rollout-....jsonl` entries, at most 5 sessions per provider per project, each at most 50 MiB (larger are skipped), plus `manifest.json` `{"project": "<name>", "sessions": [{"provider":"claude|codex","id":"<uuid>","file":"claude/<id>.jsonl","cwd":"<absolute cwd it was recorded in>","mtime":<unix>}]}`.

## Account API (user bearer, prefix `/api/cloud-computer/sync`; every reply `{ok:true,...}` or `{ok:false, code, message, error}`)

Eligibility is `Eligibility::authorize` (Pro/trial, flags). None of these needs the computer to be running. All are rate limited (240/min per user).

- `PUT /macs/{deviceId}` body `{publicKey, name}` -> `{ok, mac:{id,name,publicKey}}`. Max 5 Macs per account (409 `too_many_macs`; the oldest unused is replaced if `replace:true`).
- `GET /` -> `{ok, enabled:true, vmKey:string|null, macs:[{id,name,publicKey,lastSeenAt}], projects:[Project], usedBytes, limitBytes}`.
  `Project = {name, projectKey, upSeq, upHead|null, upSyncedAt|null, upAppliedSeq, appliedAt|null, state:'pending'|'synced'|'diverged'|'skipped'|'error', reason|null, resync:bool, cloudSeq, cloudHead|null, cloudAt|null, transcriptsSeq, transcriptsAppliedSeq, bytes}`.
  `state`: `pending` = uploaded but not yet applied on the VM; `synced` = applied; `diverged` = the VM reported local changes it would have overwritten; `skipped` = Mac said not syncable (`reason`: `too_large|no_files|disabled|...`); `error` = the VM could not apply (`reason`).
- `POST /projects` body `{projectKey, name, skipped?:{reason}}` -> `{ok, project:Project}` (idempotent; returns the granted `name`; sets `resync:true` when the VM has no copy because the volume was removed).
- `PUT /projects/{name}/up?kind=code|transcripts&seq=N&baseSeq=M&head=<40hex|->&sha256=<64hex>` raw body (`application/octet-stream`, sealed stream, streamed to disk, never buffered in memory). 409 `seq_conflict` `{expected}` when `seq != lastSeq+1` (the client re-reads `GET /` and retries); 409 `resync_required` when `resync` is true and `baseSeq != 0`; 413 `too_large` (> `cloud_workspaces.sync_max_blob_bytes`, default 536870912); 413 `quota_exceeded` (account over `sync_quota_bytes`, default 5368709120); 422 `sha_mismatch`. Returns `{ok, project}`. On success: `up_seq = seq`, `state='pending'`, `resync=false` if `baseSeq == 0`.
- `GET /down` -> `{ok, items:[{id, project, kind, seq, baseSeq, head, bytes, sha256, createdAt}]}` = un-acked `down` blobs addressed to the calling Mac (`?mac=<deviceId>` selects which Mac; required).
- `GET /down/{id}` raw ciphertext download (Content-Type octet-stream, supports `Range`). `POST /down/{id}/ack` body `{applied:bool, error?:string}`; an acked blob is deleted after 24 h.
- `DELETE /projects/{name}` removes the cloud copy record and blobs (the VM folder is removed by the VM at its next drain); used when a project is removed from sync.

The existing state object `S.computer` gains: `sync: { vmKeyReady: bool, pending: int, applying: bool, usedBytes, limitBytes }` and each `S.computer.projects[]` entry gains `source: 'mac'|'cloud'`, `syncedAt: iso|null`, `syncState: 'pending'|'synced'|'diverged'|'skipped'|'error'|null`. (Projects the Host reports and projects from `cloud_sync_projects` are merged by `name`.)

## Runtime API (VM runtime bearer, prefix `/api/cloud-runtime/{workspace}/sync`; computer workspaces only, 403 otherwise)

- `POST /key` body `{publicKey}` -> `{ok}` (idempotent; a different key replaces the old and sets every project `resync=true`).
- `GET /macs` -> `{ok, macs:[{id, publicKey}]}`.
- `GET /pending` -> `{ok, items:[{id, project, kind, seq, baseSeq, head, bytes, sha256}], removed:[name], resync:[name]}` ordered by project then seq; `removed` lists projects the Mac removed from sync.
- `GET /blobs/{id}` raw ciphertext (Range supported). `POST /blobs/{id}/applied` body `{ok:bool, head?:string, state?:'synced'|'diverged', error?:string, needFull?:bool}`: success sets `up_applied_seq`, `applied_at`, `state`; `needFull` sets `resync=true`.
- `PUT /projects/{name}/down?kind=&seq=&baseSeq=&head=&sha256=&mac=<macId>` raw sealed stream to one Mac (VM uploads once per registered Mac). Server assigns nothing: the VM keeps its own down seq per kind (it asks `GET /state` first).
- `GET /state` -> `{ok, projects:[{name, downSeq, transcriptsDownSeq, upAppliedSeq, upHead}]}`.
- `POST /status` body `{applying:bool}` (shown to the phone as "Updating files…").
Blob retention: keep the 3 newest per (project, direction, kind) plus any un-applied; delete older ones.

## Behaviour contracts

- **VM boot:** supervisor starts the Host only after the pending inbox is drained, bounded by 120 s; past that it starts the Host anyway and keeps draining in the background. A first full code bundle of a large project can take minutes: report `applying:true` throughout.
- **VM apply (code):** all git and file work runs as uid 1001 (or via `runAsUser`), never as root inside a 1001-writable tree. Receive into a 1001-owned scratch dir under `/data/.vibyra-tmp`, a bare shadow repo at `/data/.vibyra-shadow/<name>.git` (hooksPath off, clean filters blanked, `GIT_TERMINAL_PROMPT=0`), then update `/data/projects/<name>` staged in `.<name>.syncing` and renamed (invisible to Host adoption). Never overwrite an unsynced VM edit: if the project worktree differs from the last applied snapshot, take a cloud snapshot first (so it returns to the Mac), do NOT touch the files, report `{ok:true, state:'diverged'}`.
- **VM return path (code):** snapshot a project (full tree vs the shadow chain) when its worktree changed and was quiet for 60 s, every 5 minutes while the computer runs, and in the graceful-stop path before the Host is killed (budget 8 s). Encrypt once per Mac key and upload `down`.
- **Mac up path:** debounce 15 s after a file change (and a 2-minute sweep, focus loss, and a final flush on system sleep); skip when the snapshot tree equals the last uploaded tree; incremental when `GET /` says `upAppliedSeq >= upSeq` and `resync` is false, else full.
- **Mac down path:** poll `GET /down?mac=` every 60 s while the app runs (and on wake), fetch each bundle into the project's shadow repo as `refs/vibyra/cloud`, show "Cloud changed N files in X"; applying to the working tree always goes through the existing three-way review (`cloud_merge`), never silently, unless the user turned on "apply safe cloud changes automatically" (default OFF) and the Mac files touched are unchanged since the last snapshot.
- **Transcripts:** Mac packs the latest sessions of each Claude/Codex whose recorded `cwd` equals the project root (Claude: `~/.claude/projects/<cwd with every non-alphanumeric char replaced by "-">/<uuid>.jsonl`; Codex: `~/.codex/sessions/YYYY/MM/DD/rollout-*-<uuid>.jsonl` whose first `session_meta` line has `payload.cwd` equal to the root). On the VM they are placed under `$HOME/.claude/projects/-data-projects-<name>/<id>.jsonl` and `$HOME/.codex/sessions/<same relative date path>/` with the recorded `cwd` rewritten JSON-aware (top-level `cwd` field and `session_meta.payload.cwd` only) to `/data/projects/<name>`; a file that already exists on the VM with a newer mtime is kept. The return path mirrors this (VM cwd rewritten to the Mac root). One owner at a time is not enforced; the newer-mtime-wins rule is.

## Settings and consent

Mac (desktop): Settings > Phone > Cloud computer gets "Keep my projects ready in the cloud" (default ON for Pro/trial accounts after a ONE-TIME consent dialog that says plainly: project files, including uncommitted work but excluding ignored files and detected secrets, are encrypted on this Mac so only your cloud computer can read them, and stored on Vibyra servers; optional: include agent conversations (default on), include `.env` files (default off)), a per-project switch, a status line (last synced, held-back files count), "Remove my projects from the cloud". The consent version is stored with the settings; changing the text bumps it.

## Backend notes (implemented in `backend/`, 2026-10-03)

- Errors: every refusal is `{ok:false, code, message, error}`. Codes: `not_eligible` (the `Eligibility::authorize` status is kept: 402/403/503), `invalid_request` 422, `unknown_project`/`unknown_mac`/`unknown_blob` 404, `seq_conflict` 409 (+`expected`), `resync_required` 409, `too_many_macs` 409, `name_taken` 409, `too_large`/`quota_exceeded` 413, `sha_mismatch`/`empty_body` 422. Runtime: bad bearer 401, non-computer workspace 403.
- Storage: disk `cloud_workspaces.sync_disk` (default `cloud-sync`, a local disk at `CLOUD_SYNC_DISK_ROOT` or `storage/app/cloud-sync`); files at `<userId>/<projectId>/<blobUuid>`. Upload is read in 1 MiB chunks into a scratch file (cap + sha256 checked as bytes arrive, over-cap or mismatch deletes it), then streamed to the disk. A blob id is a uuid.
- `PUT .../up` `baseSeq` is optional (default 0), must be lower than `seq`; `head` optional (`-` = none). Seq is tracked per kind: `upSeq` = code, `transcriptsSeq` = transcripts (Project.transcriptsSeq is the UP transcripts seq). A transcripts upload never clears `resync` or changes `state`. `resync` clears on an accepted full (`baseSeq 0`) code upload. A full upload marks older un-applied up blobs of that kind superseded.
- `PUT .../down` (runtime): `mac` is the Mac's deviceId; accepted `seq` is `max(1, last)` or `last+1` per kind (the VM repeats a number once per Mac); the same (mac, kind, seq) replaces the earlier copy. Project `cloudSeq/cloudHead/cloudAt` = latest code down upload.
- Names: unique per account across sync projects AND clone-queue projects (`cloud_computer_projects`); a clash gets `-<first 4 hex>` (8/16/32 if that is taken too). Re-granting the same projectKey is idempotent and ignores the new name; re-adding a removed project forces `resync`.
- `DELETE /projects/{name}` keeps a tombstone (`removed` in `GET /pending`) until a day after the VM listed it, or `computer_stopped_days` (min 7) if it never did. Idempotent.
- `pending` hides incremental code blobs of a project with `resync=true` (their base is gone) and lists `resync:[names]`. A failed apply (`ok:false`) sets state `error` + `resync`; `needFull` sets state `pending` + `resync`. A failed blob is not listed again.
- A different VM key, or Retention removing the stopped computer's volume, deletes every `up` blob (they are unreadable), sets every project `resync=true`, clears applied seqs/`appliedAt`, and (volume removal) clears `vmKey`. `down` blobs stay. A project granted after the volume went starts with `resync=true`.
- Retention: keep the 3 newest blobs per (project, direction, kind, recipient) plus any un-applied/un-failed; acked down blobs go 24 h after the ack; never-acked down blobs after 30 days; quota is checked as `used + new bytes` after first dropping what retention would drop anyway. `vibyra:cloud-sync-prune` runs hourly.
- `S.computer.sync.applying` is true only for 10 minutes after the last `POST /status {applying:true}`. `S.computer.projects[]` entries: sync projects are `source:'mac'`; `syncedAt` = when the cloud computer last applied code; `syncState` = project state. Every other project gets `source:'cloud'`, nulls. `ActivityAndListingTest` was updated for the three new keys.
- Account deletion: `AccountCleanup::prepare` deletes the account's sync files and rows first (a retried deletion has nothing left to clean).
- A 4th table `cloud_sync_vm_keys` (the VM public key + applying flag) was added to the three in the plan.

## Sync notes (Mac core, `desktop-tauri/src-tauri/crates/vibyra-sync`, 2026-10-02)

- **VSYNC1 chunking:** a plaintext of exactly 65536 bytes is ONE final chunk (no trailing empty chunk); an empty plaintext is one empty final chunk. The writer looks one byte ahead to know which chunk is last; the reader decides "final" by whether another length prefix follows. `docs/cloud-sync-vectors.json` (generated by `vibyra-sync gen-vectors`, checked by `cargo test -p vibyra-sync --test crypto`, and independently opened with Node's `crypto`) fixes the recipient and ephemeral secrets and holds sealed hex for the small cases, `sealedLength`/`sealedSha256` for 65536/65537/200000, and reject streams (wrong magic, flipped tag/ciphertext, truncation, trailing byte/chunk, oversize length, header only). A reader writes plaintext as chunks authenticate, so it must discard its output when the stream fails at the end.
- **Mac up path:** every sync does `GET /` (needs `vmKey`, else nothing is done) and `POST /projects` (learns `upSeq/upHead/upAppliedSeq/resync` and the granted name), then `seq = upSeq + 1`. Incremental only when `resync` is false, `upSeq > 0`, `upAppliedSeq >= upSeq` and the cloud's `upHead` commit exists in the Mac's shadow repo; the bundle then excludes that head and `baseSeq = upSeq`. `seq_conflict` and `resync_required` re-read the project and retry (3 tries; `resync_required` forces a full). The Mac proposes the name it was granted before, else the slug.
- **Not syncable:** when the files that would be tracked add up to more than the per-project cap (default 500 MiB) the whole project is skipped (`POST /projects {skipped:{reason:'too_large'}}`), not trimmed; an empty or all-secret folder reports `no_files`. Files over 20 MiB, symlinks and nested repositories are skipped individually and listed locally as `skipped`; secrets are `held_back`. `include_env` lets `.env`/`.envrc` files through by name only: private keys, credential files and any file whose content looks like a key or token stay held back.
- **Snapshot chain:** `refs/vibyra/snap` in `<state>/cloud-sync/<projectKey>/shadow.git` advances only when the tree changes; "unchanged" for upload purposes compares the tree with the last uploaded tree. Blobs are written as loose objects from the bytes that were scanned (no `git add`, no filters, no re-read).
- **Down path:** the VM's down bundles must carry exactly `refs/vibyra/cloud`. An incremental down bundle needs its prerequisite in the Mac's shadow repo, so the VM should chain its cloud snapshots on a snapshot the Mac has (for example the last Mac snapshot it applied) or send a full bundle (`baseSeq 0`). A blob the Mac cannot open or apply is acked `{applied:false, error}`. A blob for a project name this Mac has no local state for is left un-acked. Changes are reported against `base` = merge-base of the cloud head and the Mac's last snapshot (fallback: the last uploaded snapshot); only the newest cloud snapshot per project is kept pending, because each is a full tree.
- **Transcripts:** the tar starts with `manifest.json` and is deterministic for unchanged sessions (the Mac skips the upload when its SHA-256 equals the last one). The codex date folder on receipt is taken from the `rollout-YYYY-MM-DDT...` file name. The cwd rewrite changes the top-level `cwd` and, for a top-level `"type":"session_meta"`, `payload.cwd`, and also a cwd that is a subfolder of the old root (tail kept); `turn_context` payloads are left alone as the contract says. Returned conversations are written into the Mac's `~/.claude` / `~/.codex` by `poll_down` without a review (they are not working-tree files); a local file with an equal or newer mtime is kept.
- **Secret key storage:** the Mac key goes to the Keychain through `/usr/bin/security` (the secret is briefly in that process's argv) and falls back to a 0600 file under `<state>/cloud-sync/secrets/`. `device.json` holds only the device id and public key.
- **CLI:** `vibyra-sync` keeps its own state under `<config dir>/vibyra-sync-cli` (override `VIBYRA_SYNC_STATE_DIR`; `VIBYRA_SYNC_FILE_KEYS=1` skips the Keychain) and uses the absolute folder path as the project id.

## vm notes (cloud-runtime, 2026-10-02)

Files: `cloud-runtime/src/sync-{crypto,tar,key,client,git,worktree,state,apply,snapshot,transcripts,loop,process,worker}.mjs`; wiring is `computer.mjs` (boot drain before `host.start()`, final pass) and `graceful-stop.mjs` (`finalSync` hook), tests `cloud-runtime/tests/sync-*.test.mjs`. `sync-crypto` matches `docs/cloud-sync-vectors.json` byte for byte (all 6 cases, all rejects).
- **Process model.** The root supervisor only creates `/data/.vibyra-sync`, `/data/.vibyra-shadow`, `/data/.vibyra-tmp` (safe-dirs, directly under `/data`) and spawns `sync-worker.mjs serve` as uid 1001 with a fixed env. The worker does ALL file/git/crypto work and the HTTP calls itself (it re-reads the runtime token file, which 1001 can read anyway). `final <budgetMs>` is a one-shot worker. Git runs with no hooks/system/global config, no filters, byte-exact `hash-object --no-filters`, `fetch.fsckObjects`; the project's own `.git` is never read (git runs with the shadow repo as GIT_DIR and the project folder as work tree).
- **State.** Key `/data/.vibyra-sync/key` (64 hex, 0400); per-project JSON `/data/.vibyra-sync/state/<name>.json` (last tree, applied seq + report, cloud head/seq, Mac cwd, sent transcripts). A project is "managed" (snapshotted, removable) only if `/data/.vibyra-shadow/<name>.git` exists, i.e. a Mac snapshot was applied; GitHub-cloned projects are never returned or removed. The public key is published (idempotent) at every worker start, so a volume reset (new key) publishes the new key by itself.
- **Apply.** Verify `sha256` of the sealed blob, open, `git bundle verify` (missing prerequisite -> `{ok:false,needFull:true}`), exactly one ref `refs/vibyra/snap` whose sha equals `head`, fetch to `refs/vibyra/incoming`, diff the working folder's current tree against the new tree and write only the changed files (staged in `/data/projects/.<name>.syncing`, renamed per file). Ignored files and `.git` are untouched. Symlinks/gitlinks are never created, `.git`/`..` path parts are refused. Items with `seq <=` the recorded applied seq are answered from the record (a lost report is never replayed over newer files). `resync` projects answer `needFull` for any `baseSeq != 0` item.
- **Diverged** (simplest reading): the folder is "unchanged" when its tree equals the last applied snapshot tree OR the last tree this VM returned to the Mac (the Mac has seen it), or an interrupted apply left the `applying` marker, or (first apply) the folder is empty. Anything else => cloud snapshot first, files untouched, `{ok:true,head,state:'diverged'}`; the bundle is still fetched so the chain continues.
- **Return.** Snapshot rules: non-ignored regular files <= 20 MiB, no symlinks/`.git`; new files that look like secrets (`.env*` except `.example/.sample/.template`, `*.pem/key/p12`, `id_*`, `.npmrc`...) are skipped unless the applied snapshot already contained them. First cloud commit is parentless with `baseSeq=0`; later ones have the previous cloud commit as parent and `baseSeq = downSeq` (only when `GET state.downSeq` equals what the VM last sent, else a fresh parentless full). Commit message trailer `Vibyra-Base: <last applied snap sha|none>`. seq = `GET state` `downSeq`+1 (`transcriptsDownSeq`+1; transcripts use `baseSeq=0 head=-`). One sealed upload per `GET macs` entry; on any failure the local ref is rolled back and the retry reuses the same seq (the backend should treat a repeat for a Mac that already got it as idempotent or 409; the VM then retries next cycle).
- **Timing.** Drain every 5 s (backoff to 60 s on errors), change poll every 10 s (stat fingerprint of non-ignored files), snapshot after 60 s quiet or every 5 min while edits continue, transcripts at most every 5 min. First tick after boot checks every project at once (an edit lost in a crash is returned). `status{applying:false}` is posted at worker start to clear a flag a killed worker left. Final pass runs in the graceful-stop path after the Host/terminals left (or the grace expired) and before `sync`/SIGKILL, 8 s budget, only for requested stops (a lease expiry just halts the worker); `main.mjs` extends its hard-kill timer by 8 s for requested stops.
- **Transcripts.** Accepted tar names: `manifest.json`, `claude/<id>.jsonl`, `codex/[YYYY/MM/DD/]rollout-*.jsonl` (the date path is taken from the filename when absent). Claude folder = the VM project path with every non-alphanumeric character replaced by `-` (Claude's real rule; equals `-data-projects-<name>` for simple names). cwd rewrite maps the Mac root (or a path below it) to `/data/projects/<name>` and back; other cwds are untouched. Return sends only sessions changed since the last send (<= 5 per provider), manifest `cwd` = the Mac root remembered from the last received manifest, else the VM path unchanged.
- Not run here: real root/uid 1001 spawn, Docker image, Fly, Debian git 2.39 (tests ran with the local git 2.54); the Dockerfile needs no new packages.

## desktop notes (Mac app, 2026-10-02)

No sync runs before consent (`Gate::NeedsConsent`).
- **Gate order** (worker): signed in, `cloudSync.enabled`, consent current, `GET /` says `enabled`. Anything else: no snapshot, no request; the schedule and watchers are dropped and rebuilt when it opens. A refused session or `not_eligible` pauses for 5 min (or until a settings change, "Sync now" or a new sign-in); offline pauses everything (including the poll) with 30 s, 1, 2, 5, 10, 15 min waits, cleared by wake, "Sync now" or success.
- **Triggers.** File changes (one `WorkspaceWatcher` per project, same ignore list as the code view) after 15 s of quiet, but at most 2 min after the first unsynced change; a 2-minute sweep over every enabled project; window focus loss and app exit (waits up to 8 s) flush projects with unsynced changes; wake from sleep is detected by a wall-clock gap of over 30 s (the monotonic clock does not tick asleep) and triggers a sweep and a poll; "Sync now". A macOS will-sleep flush needs native `NSWorkspace` code and is NOT done: the debounce and focus-loss flush bound what a lid close leaves behind. One upload or poll at a time (one worker thread); the engine is blocking and never runs on the UI thread or async runtime.
- **Down path.** `poll_down` every 60 s and on wake. Each new cloud snapshot is announced once (`cloud-sync:changes`, a banner "Cloud changed N files in X", an in-app notification in the `system` category, so the OS shows it only if the user routes that category to the system). Nothing is written without the review, unless `autoApplySafe` is on and every touched file is unchanged on this Mac since the last upload and none is on the "cannot apply here" list; that quiet apply uses the same backup + `cloud_merge` path as the review, not `Engine::apply_cloud_if_clean` (which writes without a backup).
- **Review ("Cloud changes" tab of the project's cloud dialog).** base = `Side::Base`, ours = the file on disk, theirs = `Side::Theirs`, restricted to the files the cloud changed and fed to the existing `cloud_merge` (a file edited only in the cloud applies; one edited on both sides keeps the Mac version; the digest must still match at apply time; the original files and a copy of the cloud's files are backed up under `cloud-backups/sync-<projectKey>/`). Files the transfer rules refuse (credentials, `vendor/`, `node_modules`, symlinks, over 1 MiB) are listed as "cannot be applied here" and never written. "Keep my versions" dismisses the change; the Mac's files then replace the cloud's at the next sync.
- **Removal.** A project removed from settings is removed with `remove_project` only after being absent for 2 minutes, and never from an empty project list on a fresh start (a damaged settings file would otherwise delete every cloud copy). Switching a project off only stops syncing it. "Remove my projects from the cloud" (confirmed) turns sync off, then removes every project that has local sync state. `<state dir>/cloud-sync/app-projects.json` (ids, names, folders) lets a closed project be removed later.
- **Keys and server.** The device key uses the 0600 file backend (`<state dir>/cloud-sync/secrets/`), not the Keychain (its `security` command line shows the secret). State dir = the settings folder, or `VIBYRA_SYNC_STATE_DIR`. The API base is `account_api::base_url()`, so `VIBYRA_DESKTOP_API_URL=https://vibyra-stg-api.fly.dev` points the app at staging. The Mac registers once per session token (`PUT macs/{id}`, named after the computer).
- **Old flow.** "Hand off to cloud (advanced)" and "Pull from cloud" (GitHub branch) still work, now under the project menu's "More cloud options" and as tabs of the same dialog; the primary path is the per-project "Keep ready in the cloud" switch.
- **Tests.** `cargo test --lib cloud_sync` (schedule, worker gating/backoff/quit flush/removal, runner thread, watchers, status view, review and apply on a real shadow repo), `cargo test -p vibyra-core --lib cloud_sync_settings`, `node --test tests/cloudSync.test.mjs`, `node scripts/verify-cloud-sync.mjs` (mocked commands, 1280 px dark and light, screenshots in `output/cloud-sync`). Not exercised: a real account, the staging server, Mac WebKit.

## Logins (opt-in carry-over of a Codex login) - owner decision 2026-10-02

The owner asked for their Codex login to reach the cloud computer automatically. Scope and safeguards (binding):
- **Codex only**, only `$CODEX_HOME/auth.json` (default `~/.codex/auth.json`), one regular file, at most 64 KiB, JSON that parses and has no symlink in its path. Claude is NOT carried (its login is in the macOS Keychain and is not read); Claude stays the one-tap sign-in on the cloud computer. Never log, print, copy to a temp file, or put the contents on a command line anywhere (Mac, backend, VM). Tests use fixture files in temp dirs and NEVER read the real `~/.codex/auth.json`.
- **Opt-in:** a separate Mac switch "Use my Codex login in the cloud" (default OFF) with its own plain-language consent line (the login is encrypted on this Mac so only your cloud computer can read it; it lets agents on that computer act as you on Codex; sign out of Codex on the cloud computer or turn this off to revoke; refresh tokens rotate, so using Codex on both machines at once can sign one of them out). Not enabled by the general "keep my projects ready" consent. The CLI equivalent is an explicit command, never implicit.
- **Artifact:** `kind=login`, plaintext = ustar tar with exactly `codex/auth.json`; sealed with VSYNC1 to the VM key like everything else; one-way (Mac to VM only; nothing flows back).
- **Backend API (user bearer):** `PUT /api/cloud-computer/sync/login/codex?seq=N&sha256=<hex>` raw sealed body (max 256 KiB, 413 otherwise; `seq` must be > the last accepted, else 409 `seq_conflict`; the new blob replaces any older un-applied login blob immediately); `DELETE /api/cloud-computer/sync/login/codex` removes any pending blob. `GET /api/cloud-computer/sync` gains `logins: {codex: {seq, appliedSeq, pending: bool, appliedAt|null}}`.
- **Runtime API (VM bearer):** `GET sync/pending` items gain `{id, project:null, provider:'codex', kind:'login', seq, bytes, sha256}`; `GET sync/blobs/{id}` downloads; `POST sync/blobs/{id}/applied {ok, error?}`. **The blob file is deleted from storage as soon as the VM acks `applied` (ok or not), and in any case after 24 h**; only the seq/applied metadata stays. Account deletion removes any pending login blob.
- **VM:** the uid-1001 sync worker opens it, validates it is the single expected tar entry and parseable JSON, and writes `$HOME/.codex/auth.json` mode 0600 owned by the project user via a temp file in the same directory + rename; it replaces the existing file ONLY IF the VM is not already signed in to Codex or the content differs and the Mac copy is newer (seq higher than the last applied seq it recorded); it never logs contents, never keeps the plaintext anywhere else, and removes its scratch files. Host activity already reports `login.codex` from the file's presence.
- **Mac engine:** `vibyra_sync::logins` (pack the one file, refuse symlinks/oversize/non-JSON, seal, upload, remember the last sent content hash so an unchanged file is not re-sent; re-send when the file content changes, at most once per 10 minutes); CLI `vibyra-sync send-login codex` (prints only "sent"/"unchanged"/an error, never contents); desktop settings switch + consent dialog line + status ("Codex login sent 3 min ago" / "Not signed in to Codex on this Mac").

## login notes (backend/vm, 2026-10-03)

- **Backend.** Table `cloud_sync_logins` (one row per account+provider: `seq`, `applied_seq`, `applied_at`, `failed_at`, `error`, and the live blob `blob_id/path/bytes/sha256/uploaded_at`); code in `SyncLogins`, `SyncLoginController` (`PUT|DELETE sync/login/{provider}`, only `codex`, else 422 `invalid_request`; 30 requests/min on top of the 240/min sync limit). The sealed file is stored at `<userId>/logins/<uuid>`; the response of PUT and DELETE is `{ok, logins}`. A refusal order: eligibility, seq (409 `seq_conflict` + `expected`), size (413 `too_large`, also from `Content-Length`), then 422 `empty_body`/`sha_mismatch`.
- `DELETE` removes only the pending blob; `seq`/`appliedSeq` stay, so the next upload must still exceed the last accepted `seq`. `appliedSeq`/`appliedAt` change only on an `ok` ack; a failed ack deletes the file, records `failed_at` and `pending` becomes false (the Mac sees `seq > appliedSeq` and no pending blob). The 24 h sweep is part of `vibyra:cloud-sync-prune`. A new VM key or a removed volume drops any pending login and resets `appliedSeq`/`appliedAt` to 0 so the Mac can tell it must send again. Login blobs do not count toward the sync quota; `S.computer.sync.pending` includes a pending login.
- `GET sync/pending` lists login items FIRST, shaped `{id, project:null, provider:'codex', kind:'login', seq, bytes, sha256}` (no `baseSeq`/`head`). `GET sync/blobs/{id}` and `POST .../applied` accept login blob ids; after the ack the id is 404.
- **VM.** `sync-login.mjs` + `sync-login-tar.mjs`, hooked in `sync-loop.mjs` (`kind:'login'` bypasses `applyItem`). The sealed blob (<= 256 KiB) is the only scratch file; it is opened in memory, so no plaintext touches disk except the final `$HOME/.codex/auth.json`. Simplest safe reading of the replace rule: an item with `seq <=` the recorded seq (state key `_login-codex`) is a re-delivery and is answered `ok` without touching the file; otherwise it writes when the VM has no valid JSON-object `auth.json`, or its content differs (so a first carried login replaces a hand-made VM login). A `.codex` that is a symlink is refused; a symlink at `auth.json` is replaced, not followed. Failures are `{ok:false, error:<fixed generic string>}` and the seq is not recorded.
- Not tested here: root/uid-1001 ownership (tests run as the current user), a real Fly VM, a real Mac upload.

## Continue a conversation in the cloud (Host + phone) - owner request 2026-10-02

Synced transcripts already land on the VM (`$HOME/.claude/projects/-data-projects-<name>/<id>.jsonl`, `$HOME/.codex/sessions/YYYY/MM/DD/rollout-*-<id>.jsonl` with `cwd` rewritten to `/data/projects/<name>`). The phone needs to list them and resume one in a terminal.
- **Host RPC `agent.sessions {projectId}`** (permission `terminal:access`; capability `agentHistoryV1: true` in `host.state`, set only where `session.resume` is supported): returns `{sessions:[{provider:'claude'|'codex', id:<uuid>, title, updatedAt:<iso>, size:<bytes>}]}` for that project, newest first, at most 30. Claude: files in `$HOME/.claude/projects/<project path with every non-alphanumeric char replaced by '-'>/*.jsonl`; Codex: rollouts under `$HOME/.codex/sessions/**` whose first `session_meta` line has `payload.cwd` equal to the project path. `title` = the first user message text, whitespace-collapsed, at most 80 characters (fallback "Conversation"); read only the first ~64 KiB of each file; never return file contents beyond the title; skip unreadable/oversize (> 200 MiB) files and any file whose name is not `<uuid>.jsonl` / `rollout-...-<uuid>.jsonl`. No credential file is ever read.
- **`session.create` gains `resume: {provider, id}`** (valid with the existing PTY runner for claude/codex): launches `claude --resume <id>` / `codex resume <id>` with the same flags/permission mode as a fresh launch, in the project's folder; the id must be a plain UUID and its transcript must exist for this project (else error code `resume_unavailable`); the new session records that agent session id like any other so it can be resumed again after a VM sleep.
- **Phone:** inside a project on the cloud computer (and any Host that advertises `agentHistoryV1`), a "Continue a conversation" action (project row menu and the new-terminal sheet) opens a sheet listing those conversations (provider icon, title, relative time); tapping one starts the terminal with `resume` and opens it. Empty state: "No earlier conversations for this project yet. They arrive with your Mac's sync." Errors: `resume_unavailable` -> "That conversation can't be continued here. Start a new one?".

## Connect (phone consent) - owner rule 2026-10-03
Nothing cloud happens until the person ticks the box on the phone's "Connect to cloud" page.
- **API:** `POST /api/cloud-computer/connect {accept: true, consentVersion: int}` (approved market, 6/min). `accept` not true: 422 `invalid_request`. Version != `cloud_workspaces.connect_consent_version` (env `CLOUD_CONNECT_CONSENT_VERSION`, default 1): 409 `consent_outdated` `{current}`. Then the computer is created (`Computers::create`, a non-entitled account gets the normal refusal and no consent is kept), a `cloud_connect_consents` row is recorded (version, `source=phone`, user agent, `ip_hash` = sha256(ip + app key), never the raw IP), and `terms_accepted_at` is set (the connect text covers the cloud terms; no terms sheet at the first wake). Repeat calls add another record and return the state. Reply = `GET /api/cloud-computer`.
- **State:** `GET /api/cloud-computer` gains `connected` (newest non-revoked consent, version >= current) and `consentVersion` (current). It only auto-creates the computer once connected, so a never-connected account reads `computer: null`. `POST /api/cloud-computer` (old create) is 409 `connect_required` until connected.
- **Mac:** `GET /sync` gains `consent: {version, acceptedAt} | null`. The worker, when signed in, `cloudSync.enabled` and not agreed on the Mac, reads `GET /` (at most every 30 s) and treats `consent.version >= CLOUD_SYNC_CONSENT_VERSION` as its consent without writing settings; the Mac's off switch still wins. Status gains `consentFromPhone` ("Turned on from your iPhone" in Settings); the gate reads `starting` and `needsConsent` stays false until the first answer, so the Mac dialog never flashes. Tests: `ConnectConsentTest`, `worker_tests_phone.rs`.

## Sync v2 (backend, 2026-10-06; plan: docs/cloud-sync-v2-plan.md, branch fix/cloud-sync-v2-20261006)
- `GET /` adds `connected: bool` (the account agreement is current). A Mac closes its gate on `false`; it never treats
  `connect_required` as a project failure.
- `PUT macs/{deviceId}/status` (eligible only, **no agreement needed**, so a paused Mac can say so; also a check-in):
  `{paused, gate?, current?: {projectKey, kind: code|transcripts, sent, total}|null, projects?: [{projectKey,
  phase: queued|preparing|uploading|done|error, code?, message?, bytes?}]}` → `{ok:true}`. Unknown device → 404
  `mac_unknown`: register again with `PUT macs/{deviceId}` once `connected`. Send every 15 s while sending, 60 s idle or
  paused. A report counts for 150 s (`current` only for 45 s); with no check-in/report for 150 s the Mac is `offline`.
  `bytes` on a project lets the phone say "3.5 GB of 500 MB" for `too_large`.
- `POST repair {projectKey?}` (6/min per account, approved market, needs the agreement): non-destructive "Sync again".
  Every live ticked project (or the one) gets `resync: true` (next upload must be full, `baseSeq 0`); `error`/`skipped`
  go back to `pending`. Diverged projects are left alone. Wakes Cloud at once. → `{ok, repaired, projects}`.
- The server wakes Cloud itself (`Wake::forSync`, no phone session, every wake check still applies): after any up blob,
  up-part completion or login lands; on a grant, a non-paused report or a `?mac=` check-in while uploads wait or ticked
  projects have no VM key yet. At most once per 2 min, at most 3 starts for the same oldest unapplied upload (then a
  person's repair), never within 30 min of a failed boot. Clients never need to call `wake` for sync.
- The computer stays up while synced work moves (uploads to apply, applying, or a Mac reporting `current`); each upload,
  apply, `status{applying:true}` and Mac progress refreshes its idle clock; work stalled 30 min no longer holds it.
- Runtime `POST sync/status` also takes `keyOk?` and `lastError?: {code, message?, project?}|null` (null clears; left out
  keeps). Shown in `GET /api/cloud-computer` `computer.sync.vm: {keyOk, lastError}`.
- Runtime `POST sync/blobs/{id}/applied` also takes `code` and `message`; `code` wins over free-text `error` as the stored
  reason. `key_mismatch`, `needs_full` or `needFull:true` → blob failed, project `pending` with reason `needs_full` and
  `resync` (the Mac resends; never an error to the person). Other codes → project `error` with that reason.
- `GET sync/pending` `removed`: names not yet seen, or first seen under 5 min ago (one retry window), no longer a day.
  An incremental skipped for a resync project sets `reason: needs_full`.
- Disconnect (`DELETE /connect`) is the explicit "delete my Cloud copy"; a second one with nothing agreed and nothing
  kept is a no-op. Never offer it as a fix.
- Limits on every `/api/cloud-computer` route are per account (bearer hash), not per IP.
