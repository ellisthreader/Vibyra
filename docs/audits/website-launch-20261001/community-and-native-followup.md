# Community release enforcement and native provider compatibility — 2026-10-01

## Candidate community enforcement

The deployed baseline carried `config/legal.php:community_enabled=false` but never enforced it. The candidate now reuses the existing main checkout CommunityAvailability response contract: authenticated content creation returns 503 `community_unavailable` with no-store before provider calls or writes. It guards publishing (including private uploads), listing edits, comments, new reactions and asset generation. Public/unlisted transitions and review approval are also blocked. Private visibility, deletion, unlike, reports, status and review denial remain available. The command declines queued deployment; the provider stops previously queued jobs before provisioning.

By explicit release task scope, previously published public list/preview/static demo GET responses remain readable. This differs deliberately from the main checkout's stricter RequireCommunityRelease middleware which closes public reads too. Main stronger protections were not weakened. No routes/bootstrap/owner source changed here. A flag cannot retract an existing external Railway URL or cancel an already-running deployment; inventory/retirement remains an operations task if needed.

Validation: CommunityReleaseGateTest 3 tests / 38 assertions proves closed mutation routes, preserved reads and takedown/report functions, blocked approval/visibility, and stopped queued provisioning. CommunityPublishingCoreTest 20/179, CommunityPublishingHostedDemoTest 26/277, RuntimeDeploymentQueueTest 2/5, RailwayRuntimeDeploymentServiceTest 21/88 pass individually. All warnings are the known missing isolated backend/.env file; synthetic test APP_KEY used, no production configuration read. `git diff --check` passes.

## Native download provider sign-in — remaining release blocker

Local saved live download catalog (`Vibyra/docs/audits/website-launch-readiness-2026-10-01-evidence/download-catalog.json`) advertises Windows 0.6.3, Linux/AppImage+deb 0.8.10 and macOS arm64/x64 0.8.7. Source provenance note `output/desktop-connection-candidate-2026-09-25/RELEASE-0.8.10-HOST-DISCOVERY.md` identifies commit `63d5b676bde0055b8f3bd5eb8a6eec9ab13cfec8` as the 0.8.10 base. At that commit `desktop-tauri/src-tauri/src/account_oauth.rs:28-32` sends only deviceName/installId to OAuth start; polling at line93 uses request_raw with no flow-secret header. Candidate `backend/app/Services/Auth/DesktopProviderOAuthFlow.php:32-35` explicitly rejects an unbound native flow without a 32–256-character flowSecret. Therefore this 0.8.10 client source is incompatible with secure provider sign-in. Current main has the necessary generated-secret body and X-Vibyra-Flow-Secret polling header, but its new helper is untracked local work, not evidence of a shipped client.

Exact public download binaries were not executed or downloaded, and local evidence does not prove binary-to-source identity for every public platform. Treat all advertised builds as unverified for this new contract; do not claim the working current local source proves they work. Publish compatible signed clients, verify each public artifact's hash and provider start/poll contract, or make unsupported provider access explicitly unavailable with a usable update path. Keep server flow binding enforced. The documented 0.8.11/build14 macOS package is review-candidate-only and was never published; it cannot establish public compatibility. No native artifact was executed and no production action was taken.
