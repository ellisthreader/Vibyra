# Live website launch readiness — 1 October 2026

**Decision: not ready for an unrestricted customer/commercial launch.** The marketing website, owner login and consented traffic collection are working, but account-security defects and incomplete commercial operations remain. This is a report-only audit, not a remediation or deployment.

Sanitized route/asset results, runtime source hashes, scheduler observations and per-file test outcomes are retained in [the evidence directory](website-launch-readiness-2026-10-01-evidence/).

## Scope and provenance

- Public origin: `https://vibyra.net`; also probed `https://vibyra-production.up.railway.app`. The owner does not own `vibyra.app`.
- Railway production service `Vibyra`, deployment `0b32c7bc-d307-4697-a4bc-f9d142d22bb2`, source `0a02f32a5a6244ac942903d97d9bb69d226ed486`. All 1,074 compared immutable runtime source files matched the detached audit checkout. The deployment remained unchanged at the final inspection.
- Reviewed public marketing, downloads, benchmarks, authentication, account/billing/checkout, legal/support, owner analytics, and website-reachable publishing/FAQ code. Three bounded reviewers covered authentication, billing/data, and frontend/configuration; the primary reviewer checked high findings against source.
- Browser checks exercised the homepage, iOS CTA, annual checkout account gate, password login and owner dashboard. HTTP checks covered additional routes and referenced initial JS/CSS assets. This is not exhaustive device/accessibility testing or a new audit of every native app, connector, relay and worker endpoint.
- No purchase, refund, real customer signup, email send, malicious upload, production exploit or load test was performed. Installer execution, store approval, backup restoration and external email delivery remain acceptance work. Public benchmarks were checked for route/assets availability, not independently remeasured model performance.

At **13:57:09 UTC / 14:57 BST**, the owner-authorized transaction cleared website analytics only: 21 events, zero daily rollups and three ingestion-counter rows. ## What is and is not test mode

Confirmed production/debug-off environment; Stripe environment string says live, but checkout is disabled and credentials are absent. Apple environment says Production; no sandbox review accounts are allowlisted. Turnstile keys are configured and not test-shaped. Deterministic/local moderation is enabled; temporary publish-review bypass and force-approve switches are both false. Optional paid remote/AI moderation is disabled, which is distinct from bypassing local moderation.

The marketing hero and sample-phone interactions are intentionally labelled demos. Their simulated behavior does not establish that backend operations are in test mode. Mail-to-log, placeholder sender, legacy manual entitlements and wrong-domain return/contact URLs are the concrete unfinished setup found here.

## Validation and what is solid

- HTTPS redirects work; legacy TLS 1.0/1.1 were refused. Session cookies are Secure, HttpOnly and SameSite=Lax. Production debug is off. Sensitive file probes returned 404, and foreign-origin credentialed CORS was not allowed in checked responses.
- Anonymous owner/account/billing data requests were denied. Owner access uses a verified allowlist; named Accounts correctly returns 428 without second-factor setup/step-up. Password login and session regeneration worked.
- Unknown/declined analytics events were rejected; consented page/CTA/engagement events persisted, appeared in owner reporting and were removed on withdrawal before the reset. “Active · 5m” means recent engagement, not a live socket or exact person count. Named clicks cover selected CTAs, not every click. GeoLite database/key are now present; actual country accuracy was not independently tested.
- V2 Stripe code validates signatures, server-owned prices/amounts and environment, with idempotent wallet grants. This source assurance does not replace a live payment lifecycle test.
- Initial referenced JS/CSS asset HEAD checks and all five installer HEAD checks returned 200. Public page shells were available through the crawler path; unverified ordinary requests hit the human gate. `/app` was the confirmed 500, and `/sitemap.xml` was absent (lower-priority SEO follow-up).
- Scheduler and three queue workers were present. Queued/failed job counts were both zero at inspection. Scheduler failures remain a separate issue. Backup/restore, monitoring delivery, service quotas and failover were not proven by these observations.
- PHPUnit ran file by file on the exact checkout: **242 files, 232 OK, 10 not OK**. Local PHP was 8.5.10 versus production 8.3.15. These are file outcomes, not 242 individual assertions or ten proven exploits.
- Failed files: AuthThrottleSeparation, CloudSecurityHeaders, ProductionProcessTopology, RemoteAccountAtomicity, RemoteAccountSecurity, RemoteWebClient, VibesAutoGuardrails, VibyraAuthReferralApi, VibyraCors and VibyraProjectPreviewSecurityApi. Missing headers and `/app` failures reproduce live. Some others involve absent snapshot fixtures, path/HOME assumptions or stale CORS expectations; remote account atomicity/revocation and throttle assertions need separate investigation rather than being waived. The full baseline is not green.
- npm production audit reported zero advisories. A targeted current-source credential-pattern scan found no matches; this was not a full Git-history secret audit.

The earlier owner “Analytics unavailable” was a measured HTTP 502 during the Railway deployment replacement at 13:39:25 UTC. Fresh owner requests then succeeded. It was not evidence that collection had stopped. The lack of retry made a transient outage remain visible.

## Recommended release sequence

1. Prepare an isolated reviewed patch from the exact deployed SHA for authentication, recovery/session revocation, hosted-content isolation, browser headers and bot/spend controls. Port durable fixes back to the development source so the next snapshot cannot remove them.
2. Complete email delivery, owned-domain links, browser recovery and owner TOTP setup. Resolve the failing `/app` route and scheduled commands.
3. Complete billing and store safeguards, align FAQ/marketing/installer availability, and correct checkout analytics. Keep unavailable products clearly unavailable until tested.
4. Re-run focused security tests, investigate the remaining baseline failures, build the exact frontend, and verify the candidate in staging. Then use a reviewed deployment and rollback plan, verify runtime hashes and repeat live checks.
5. Before opening paid acquisition, retain evidence of account signup/verification/recovery, payment/refund/cancellation, signed installer installation, consented funnel reporting, backups restored successfully, and alerts delivered to a monitored destination.

No source fix or new deployment was performed as part of this audit. The analytics reset was the explicit production data change requested for this phase.
