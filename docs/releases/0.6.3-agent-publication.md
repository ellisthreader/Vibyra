# Agent reliability release 0.6.3

The published baseline was 0.6.1. Candidate 0.6.2 contained the teammate
dialog and save-retry repairs but was never published. Native acceptance found
that daily routine creation still failed with a missing `minute_of_day` field.

0.6.3 includes the teammate repairs, preserves the renderer's `minuteOfDay`
schedule contract and accepts legacy snake-case persisted schedules. It also
adds release notes and runs the Agent browser regressions in package CI.

## Source and validation

- The implementation starts from reviewed 0.6.2 source `c7b469749ac5d649e457c9f5fa609ff8c348487c`.
- `routine_wire` reproduced two failures before the fix and passes after it:
  renderer create/edit/reopen for all schedule types, paused-state preservation,
  and legacy schedule compatibility.
- The reviewed 0.6.2 native AppImage completed actual teammate creation,
  configuration, memory addition, skill installation/assignment and Claude
  chats using all three saved context markers. Account verification used a
  loopback fixture; Agent commands, SQLite and provider execution were real.
- Both real provider context checks passed (Claude and Codex, two fresh
  sessions each). These core checks are separate from packaged UI acceptance.
- Original worktrees, account databases and active user windows are preserved.
  The native acceptance account uses isolated XDG folders and a private display.

The corrected local native build reopened the same teammate and conversations,
created and edited a daily routine, and ran it automatically at its configured
wall-clock time. Its completed result contained the brief, memory and skill
markers. A Codex teammate created through the same native UI also completed its
context check. Evidence is in `0.6.3-agent/native-checks.json`; the screenshot
is a local native build, not the final signed package.

Final signed Debian acceptance also passed: prior state reopened, a weekday
schedule saved while preserving its paused state, the resumed schedule ran
with all expected context markers, and denying a Codex overwrite preserved
the existing file. Account verification used the loopback fixture; native IPC,
SQLite, provider calls and the scheduler were real. Windows interactive provider
acceptance was not run locally; CI verified its installer and launch.

The complete signed package workflow passed: [run 34225371322](https://github.com/ellisthreader/Vibyra/actions/runs/34225371322),
source `99ec76c895430d63fc09c776b0906d432eb15e49`. Linux CI passed 781 frontend
tests, 342 core unit tests, 252 desktop tests, all integration/signature targets,
22 teammate browser checks and seven integration UI scenarios. Two opt-in native
tests remained ignored; real provider context checks ran separately as above.
Formatting, strict Clippy, build, dead-code and the 200-line gate passed.

## Published delivery

[Release v0.6.3](https://github.com/ellisthreader/Vibyra/releases/tag/v0.6.3)
is public with the three signed packages and their verification sidecars.
Railway deployment `87b5c9e2-ccb4-42db-a935-05bf2930a23a` succeeded on
8 September 2026. It reuses the deployed backend image with updated release
metadata; no unrelated backend source was deployed.

All 36 public updater requests passed: ten older versions receive 0.6.3 on
each Windows/Linux route; current and future clients receive 204. Every public
binary download matched CI size and SHA-256, and feed signatures matched the
verified signed artifacts. See `0.6.3-agent/live-feed-checks.json`.

A real isolated 0.6.1 AppImage downloaded, installed and relaunched 0.6.3 through
the production updater. Both the replacement package and running native binary
matched the release hashes. The post-update release notes rendered correctly;
see `updater-check.json` and `updater-relaunch.png` in the evidence directory.
The local stable launcher was atomically updated and verified, preserving the
active user window. It uses 0.6.3 on next launch. Publication makes the update
available to users; it does not prove every installed client has upgraded.

The focused Agent acceptance does not establish exhaustive whole-application
coverage. Windows installer/launch passed CI, but interactive Windows provider
acceptance was not run. macOS packages are not part of this release.
