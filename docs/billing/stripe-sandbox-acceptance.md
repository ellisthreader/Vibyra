# Real Stripe sandbox acceptance

Prepared against website candidate `9a4db56`. This is an opt-in operator workflow,
not evidence that provider acceptance has run. No production billing flags, keys,
database or webhook endpoint may be changed for this exercise.

`vibyra:website-launch-readiness` reads configuration only.
`vibyra:membership-replay` retries previously verified pending/failed stored events;
it neither creates payments nor exercises webhook signatures. Existing unit and
feature tests mock Stripe. This workflow adds real hosted Checkout, canonical API
reads with the runtime restricted key, signed webhook delivery, and local state
assertions. It does not replace a browser test of Vibyra login/checkout consent,
PostgreSQL concurrency tests, or production deployment/configuration checks.

## Credentials and resources required

Use a separate Stripe **sandbox**, not live mode, with no real customer data.
Create the same five active GBP prices: monthly1999/month, annual19999/year,
tokens80=499, tokens200=999, tokens450=1999 pence. Quantity is one; no tax additions,
discounts, trials, usage meters or price switching. Configure a sandbox portal:
cancel at period end, payment-method update and invoice history on; plan/quantity
updates and retention coupons off. API version is `2026-04-22.dahlia`.

Two keys from that same sandbox are needed, loaded privately via environment:

- Runtime `STRIPE_SECRET_KEY`: `rk_test_…` with Customers, Checkout Sessions and
  Customer Portal Write; Invoices, Subscriptions, Charges, Payment Intents,
  Disputes and Invoice Payments Read. Do not broaden it to make test operations
  succeed; provider log403s identify missing runtime permissions.
- `STRIPE_SANDBOX_OPERATOR_KEY`: a separate sandbox-only key able to create test
  clocks/customers, read prices/portal configurations, advance clocks, change
  test payment methods/subscriptions, refund test payments, submit dispute
  evidence and read/resend events. A sandbox secret key is acceptable for this
  disposable operator workflow; never put it in the app runtime configuration.
- CLI-generated `whsec_…`, used only by the local webhook receiver. No public
  endpoint registration or tunnel is required for `stripe listen` forwarding.

No publishable key is required for Stripe-hosted Checkout generated by this
server workflow. Sandbox credentials/resources and human completion of hosted
test Checkout are the remaining external inputs; nothing here charges money.

### Optional anonymous sandbox

Stripe now documents `stripe sandbox create --email OWNER_EMAIL --non-interactive
--config PRIVATE_PATH` for a temporary anonymous sandbox, with no account
registration. Use a new0700 directory and capture command output privately: it
contains credentials and a claim capability URL. Never overwrite the existing
CLI profile or claim the sandbox as part of this acceptance run. Official
[sandbox documentation](https://docs.stripe.com/sandboxes) explains the isolation.

Its limited `rkcs_…` key requires explicit `STRIPE_SANDBOX_CLAIMABLE=1` in this
local helper. This does not relax the production key guard. On2026-10-01 the
claimable key could create products/prices/portal/Checkout, but Test Clock create
returned403 requiring a claimed/full key. `STRIPE_SANDBOX_NO_CLOCKS=1` explicitly
allows initial purchase/cancel/refund/dispute fixtures without clocks; renewal,
failed-renewal and expiry acceptance remain unexecuted until a full sandbox key
is provided. The claimable key cannot prove the planned restricted-key scopes.

## Isolate and start

Use the isolated candidate worktree. Ensure its backend has no `.env` containing
other service credentials and no cached config. Use a fresh shell without
production secrets (`env -i PATH="$PATH" HOME="$HOME" /bin/bash --noprofile --norc`).
From `backend/`:

```bash
test ! -e .env || exit 1
test ! -e bootstrap/cache/config.php || exit 1
umask 077
export STRIPE_PAD="$(mktemp -d "${TMPDIR:-/tmp}/vibyra-stripe-sandbox-XXXXXXXX")"
export DB_DATABASE="$STRIPE_PAD/billing.sqlite"
touch "$DB_DATABASE"
export APP_KEY="$(php -r 'echo "base64:".base64_encode(random_bytes(32));')"
cp scripts/stripe-sandbox/environment.example "$STRIPE_PAD/environment"
```

Privately fill the empty keys/resource IDs in `$STRIPE_PAD/environment`; do not
paste them into chat, shell history, screenshots or committed files. In each
terminal export the same PAD/database/APP_KEY, then load that file with
`set -a; . "$STRIPE_PAD/environment"; set +a`. Use the same APP_KEY throughout.

```bash
php scripts/stripe-sandbox-acceptance.php guard
php scripts/stripe-sandbox-acceptance.php migrate
php scripts/stripe-sandbox-acceptance.php check
export STRIPE_API_KEY="$STRIPE_SANDBOX_OPERATOR_KEY"
```

The guard refuses production, live keys, database URLs, non-SQLite connections,
cached config, shared paths and symlinked databases. It requires a real
`billing.sqlite` directly within a `vibyra-stripe-sandbox-*` temporary directory.
`migrate` is additive and never runs `migrate:fresh`. `check` makes read-only
provider requests, validating actual sandbox prices and portal settings.

In a dedicated terminal, start forwarding the exact production allowlist:

```bash
stripe listen --events checkout.session.completed,checkout.session.async_payment_succeeded,invoice.paid,invoice.payment_failed,customer.subscription.updated,customer.subscription.deleted,charge.refunded,charge.dispute.created,charge.dispute.updated,charge.dispute.closed,charge.dispute.funds_withdrawn,charge.dispute.funds_reinstated --forward-to http://127.0.0.1:8139/api/billing/webhook
```

Privately put the printed signing secret into `STRIPE_WEBHOOK_SECRET` in the
environment file and reload it in the server terminal. Start
`php artisan serve --host=127.0.0.1 --port=8139` there. The listener follows the
sandbox's default API version; verify that version matches the candidate.
Keep receiver and listener running. Do not use `--live` or `stripe trigger`:
generic trigger fixtures lack the app order/customer ownership metadata.

## Create and pay genuine app orders

```bash
php scripts/stripe-sandbox-acceptance.php seed monthly pro_monthly
php scripts/stripe-sandbox-acceptance.php seed annual pro_annual
php scripts/stripe-sandbox-acceptance.php seed small tokens_80
php scripts/stripe-sandbox-acceptance.php seed medium tokens_200
php scripts/stripe-sandbox-acceptance.php seed large tokens_450
```

Each creates one local synthetic verified account and modern wallet, calls the
real `Membership\Checkout` service using the runtime key, and returns a sandbox
Checkout URL. Repeating the same fixture resumes the same stored request/order.
Subscription fixtures have separate Stripe-clock customers; top-ups exercise
runtime customer creation. IDs persist privately in `$STRIPE_PAD/fixtures.json`.
No passwords are printed and these fixtures cannot be used to sign in.

Before payment run `assert FIXTURE pending`. Complete each returned hosted URL
with Stripe's success test card `4242424242424242`, future expiry and any CVC.
Wait for genuine webhook2xx responses, then run:

```bash
for fixture in monthly annual small medium large; do
  php scripts/stripe-sandbox-acceptance.php assert "$fixture" paid || break
done
```

Expected purchased grants:300/3600/80/200/450 tokens, respectively. Units in
reports are tokens×10000. Subscription is granted by `invoice.paid`, top-up by
canonical paid Checkout. A redirect alone must leave `pending`.

## Lifecycle cases and exact acceptance checks

All Stripe CLI commands below inherit the sandbox `STRIPE_API_KEY`. Fill only
object IDs observed from this run; keep provider JSON/results private.

| Case | Genuine provider action | Local acceptance |
|---|---|---|
| Replay | `stripe events resend evt_…` twice, using the original invoice/Checkout event from listener logs | Same `paid` assertion; no extra period or grant. For a stronger comparison save `snapshot FIXTURE` before/after and compare JSON after removing `asOf`. |
| Monthly renewal | Advance monthly fixture's clock just beyond the paid period end, wait for clock `ready` and renewal `invoice.paid` | `assert monthly renewed`: exactly2 periods and600 tokens granted. |
| Annual renewal | Advance annual fixture's separate clock to just beyond its yearly end and wait | `assert annual renewed`: exactly2 periods and7200 tokens granted. |
| Cancel | `portal monthly`; open returned URL and cancel at period end | `assert monthly cancelled`; no purchased tokens removed. Verify no plan/quantity switching UI. |
| Expire | Advance cancelled fixture past its latest paid end; wait for ready/webhooks | `assert monthly ended`; free entitlement, no further paid period. |
| Partial refund | On `small` payment, refund100 pence | `assert small partial-refund`: cumulative100 pence;160320 units reversed,639680 remain. |
| Full refund | Refund the remaining399 pence on that same payment | `assert small full-refund`: cumulative499 pence;800000 units reversed; zero remain. Replay both refund events and original paid event; result must remain identical. |
| Dispute won | Seed `dispute-win pro_monthly`, pay using Stripe's dispute test card4000000000002685, wait for dispute | `assert dispute-win disputed`; then submit `winning_evidence`, wait for dispute.closed and `assert dispute-win won`. |
| Dispute lost | Fresh `dispute-loss pro_monthly`, same dispute test card | `assert dispute-loss disputed`; submit `losing_evidence`, then `assert dispute-loss lost`: funded tokens revoked and membership restricted. |

Clock advancement (use exact end from `snapshot`; at most two billing intervals
per advance, and wait until ready before advancing again):

```bash
stripe post /v1/test_helpers/test_clocks/clock_FROM_THIS_FIXTURE/advance -d frozen_time=EPOCH_JUST_AFTER_END
```

At a renewal boundary Stripe can first create a draft invoice. If still draft,
advance the same ready clock another hour and wait for finalization/payment;
do not mark invoices paid manually. Stripe clocks do not advance Laravel time:
the read-only snapshot/assert helper evaluates entitlements at that fixture's
actual Stripe `frozen_time`; it never changes server time or production data.

Refund/evidence examples (paymentIntent comes from the local snapshot; find
matching dispute ID in this run's Stripe event log):

```bash
stripe refunds create -d payment_intent=pi_FROM_SMALL -d amount=100
stripe refunds create -d payment_intent=pi_FROM_SMALL -d amount=399
stripe disputes update dp_FROM_WIN -d 'evidence[uncategorized_text]=winning_evidence' -d submit=true
stripe disputes update dp_FROM_LOSS -d 'evidence[uncategorized_text]=losing_evidence' -d submit=true
```

Also seed `failed-renewal pro_monthly`, pay successfully, replace its saved
payment method in the sandbox with `pm_card_chargeCustomerFail`, set that method
as subscription default, then advance its clock past the paid end. Require
`invoice.payment_failed`, unchanged one-period/300-token purchased grant and
`assert failed-renewal failed-renewal`. This additionally requires the original
processed `invoice.payment_failed` event tied to that subscription and exactly
one purchased grant; merely observing an expired membership is insufficient.
Use the sandbox Dashboard for payment-method attachment/default assignment so
the provider's required confirmation steps are visible.

For transient canonical-read failures, restore the sandbox runtime permission
or connectivity and resend the exact failed genuine event. Alternatively use
`php artisan vibyra:membership-replay --limit=50` ONLY in this isolated shell.
Every final assertion refuses any pending/failed membership event in this
disposable database. Never synthesize a signature or edit a payload to pass.

## Record and stop

Record candidate SHA, sandbox ID (no keys), case/event IDs, runtime403 count,
webhook statuses and each assertion JSON/exit code. A phase failing or an
unexecuted case is an acceptance gap, not a pass. Test key validity, clock/Checkout
compatibility, real invoice shapes and live permissions remain unverified until
this workflow actually runs against Stripe.

Stop the two local processes. Remove only this run's synthetic sandbox
customers/clocks or the dedicated sandbox after evidence is saved. Delete the
private temporary directory, revoke the operator key and unset its environment.
Do not delete any live object or change production flags from these steps.
